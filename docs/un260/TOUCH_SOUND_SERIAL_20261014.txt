UN260 蜂鸣器业务命令时序修复（2026-10-14，11:23 实机日志依据）

结论与证据
本次日志明确证明 MDC(04)、Batch(06)、Speed(16) 已触发并发送 4A/01，并非漏绑定按钮。它们在同一日志时间段连续发送“业务命令 + 4A/01”，约46～51ms后发送4A/02并收到业务回复，未收到任何4A/01成功确认，第一次4A/02也没有确认，120ms后重发OFF才有确认。
ADD(39)、Auto(38)、Sort(3A) 都先收到业务回复，再发送4A/01，随后有4A/01和4A/02确认。之前只检查触摸请求和单独蜂鸣器回包，没有覆盖主控忙于处理业务命令的窗口，验证不充分。
可以确认的 UI 缺陷：串口写互斥仅防止帧字节交错，没有协调主控处理业务命令的时间；蜂鸣器从写出ON起计35ms，不等打开确认。主控内部是覆盖缓存还是忽略忙时命令，仅凭本日志不能确定；本次不声称修改了主控固件。

公共修复，不按页面或按钮名单处理
1. protocol_tx_gate 在共同发送入口记录普通命令，RX收到匹配命令的完整帧后解除该命令的等待；不同命令独立跟踪。正常业务命令仍按原路径直接发出，成功/失败确认、超时及模型更新语义不变。
2. 蜂鸣器ON通过可选发送接口：在业务回复尚未收到或串口刚活动时不插入。检查与实际写入使用同一互斥区，避免检查后又插入新业务命令的竞争。匹配回复后的短暂稳定间隔为8ms；只有蜂鸣器工作线程等待，不阻塞UI等主控确认。
3. 一次点击最多等待250ms，无回复则丢弃，不排队迟到补播。通信观察窗口300ms后解除过期记录，避免记录永久残留；原业务层自己的超时机制不变。没有新触摸不会自行补响。
4. ON确认后保持目标35ms再发OFF；ON确认最多等待120ms，缺失/失败也进入OFF清理，不重发ON。OFF仍最多3次、每次120ms；无确认时只做OFF恢复探测。实际起音间隔至少120ms。
5. 关闭屏幕声音时取消等待中的点击；正在发声则进入关闭流程，保留OFF恢复。串口关闭前停止蜂鸣器；重新启动清空通信观察状态。
6. 普通点击与手势规则、机器声音/屏幕声音独立开关均保留。没有调整任何UI布局、按钮位置或业务回调。

验证
新增主控忙窗口复现使用真实 production protocol_send、RX解析线程和蜂鸣器线程，模拟主控处理配置50ms、期间忽略新命令。旧代码：04操作 physical_on=0、dropped=2，断言失败。相同测试修复后04/06/16/38/39/3A及通用性检查67都为physical_on=1、dropped=0。
另测ON确认延迟60ms、业务无回复、等待取消、静音后恢复、退出无晚发ON；公共通信层测匹配/不匹配回复、多请求、写入竞争、正常命令优先、写失败、观察过期和重置；真实串口生命周期在O0/O2下测试成功、失败和重启。保留触摸/手势、关闭ACK丢失恢复、500ms UI阻塞、无钞与点钞、主页交互回归。
构建/升级包结果以verification中的最终报告为准。主机模拟能验证这类时序缺陷，不能替代板上实际蜂鸣器听音。新版本实机日志应显示：业务TX → 同命令RX → 4A/01 TX → 4A/01 RX → 4A/02 TX → 4A/02 RX。
