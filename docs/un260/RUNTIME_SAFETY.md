# UN260 运行故障保护与验收

本次优先保护点钞状态，不自动重启计数应用，不将故障前的 UI 数字当作控制板最终结果。恢复必须人工核对实物和控制板状态。

## 已确认问题与实现

- 现场崩溃：T-HEAD GCC 10.2 生成的圆角遮罩指令在跨零坐标计算中错误处理窄有符号数，导致圆表越界。补丁 0014 使用宽有符号中间量，并检查圆表行号、长度和偏移；0012 保留矩形端点比较的同类修复。目标指令测试与实际发布库逐字节对照。
- 直线遮罩同类审计：实际指令在减法后执行符号扩展，4320 个平移用例通过；没有为此改动正常直线绘制。
- 圆缓存：补丁 0015 先准备新资源，再替换旧表。内存失败保留原表、归还引用，临时描述符正确释放；圆角参数重复清理不会再次释放。可恢复的缓存失败只影响这次绘制，无法继续的 LVGL 断言改为终止受损进程并进入保护。
- UART：明确非阻塞、关闭继承的软硬件流控；发送锁等待和发送共用 50 ms 总期限，接收被信号打断也不延长原期限。部分发送后锁住该通道，不能拼接下一条命令或假定控制板没收到。诊断日志背压有期限，正常日志内容保留。
- 冠字号/拒钞明细内存失败不再静默忽略。通信不确定时不能先清空 UI 数据再发现 CLEAR 发不出去。

## 保护进程

应用在创建线程、初始化显示和通信前创建独立监督进程。正常 UI 循环只递增内存心跳；协议事件写固定大小共享内存，不分配、不写盘。监督进程每 100 ms 检查一次。首次心跳前期限 60 s，之后连续 10 s 无进展视为停滞；不是按帧率或单帧耗时判故障。

致命信号只记录信号、故障地址及指令地址，然后按默认行为终止进程。不会从 SIGSEGV 返回继续业务。监督进程确认原 UI 进程退出后，启动独立的原生保护显示；不依赖 LVGL、点钞协议、触摸或启动图片分配。保护显示在存盘之前启动，避免磁盘故障拖住提示。

发生故障后，禁止自动发送 RUN、CLEAR、RESET 或重新执行正常开机握手。正常服务停止仍转发终止信号，不被误记成崩溃。监督进程意外死亡时，子进程也终止，避免孤立应用继续运行。

持久证据目录 `/etc/un260-runtime-fault`：

- `pending`：未核对标记。再次开机只进入保护显示。
- `evidence.txt`：写完并同步后发布的证据，包括最后已处理的 UI 汇总、是否点钞/有待保存结果、最近 RX/TX、信号地址和模块映射。
- RX 最多保留 2048 帧、TX 最多保留 256 条事件；明确记录覆盖数量和未完成槽。RX 不等于已处理，TX 写完不等于控制板 ACK。记录不是完整交易日志，不自动重放。
- 写盘失败时尝试 `/tmp/evidence.txt`。RAM 证据必须先导出，断电不能保留。不能承诺闪存不可写或内核失效时仍持久保存。

## 人工恢复

1. 停止继续放钞，保留并分开各钞口钞票；核对或重新清点，确认控制板状态。保护页不会保证电机已停止，不发送未经确认的停机指令。
2. 先导出 `evidence.txt`、启动日志和 `dmesg`，再停止 UI 服务：`/etc/init.d/S00lvgl stop`。
3. 完成人工核对后，执行 `/usr/local/bin/un260_runtime_recover --ack-reconciled`。运行中的服务、缺失的完整证据或异常路径都会拒绝解除保护。该命令归档证据，不删除历史、不发送控制命令、不启动应用。
4. 再手工执行 `/etc/init.d/S00lvgl start`，检查自检、传感器与实物一致后继续工作。

勿以删除 `pending` 代替核对。监督进程、恢复工具和保护显示必须与应用、LVGL 库一起升级；普通完整 UPK 的安装清单明确安装两个维护工具。

## 验证与边界

主机验证涵盖真实子进程段错误、LVGL 断言、停滞、通信不确定、阻止再次启动、归档恢复、正常服务停止；真实非阻塞 socket/PTY 覆盖部分发送、并发发送、信号打断、断连、配置回读和失败清理。圆表生成和分配失败使用 ASan/UBSan；点钞协议、原始编号、报告发布、历史背压与 Sensors 生命周期使用现有回归。

固件需完成 LVGL 重建、应用交叉编译、完整 make，并核对完整/统一升级包与工厂镜像。本次本地提交仅含稳定性相关文件及匹配的 LVGL 配置前置改动，不包含现有 Quick 控件实验；完整交付包保留当前工作区已有功能，另对选定提交的应用代码独立交叉编译。

正常绘制算法、刷新周期、触摸反馈没有降级；新开销是固定内存写入、事件快照和低频监督。主机测试、编译和指令检查不能证明板上帧率不变。板上仍需验证异常启动进入 Sensors、长时间点钞、快速切页、实际串口背压、维护显示接管、升级/停启，以及开关录屏两种状态下的帧时间。

本机制面向用户态崩溃、停滞和通信失败。内核不可中断等待、整机掉电、系统级 OOM 同时杀死监督进程、硬件故障仍有边界；不能以“绝不死机”代替板上验证或控制板状态核对。
