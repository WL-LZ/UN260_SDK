# 图片稳定性与安全快速升级：四阶段实现

## 部署顺序

第一次必须安装新生成的 `UN260_UPDATE.upk` 完整包并重启：本轮同时变更应用与 liblvgl，并安装 `un260_unpack`。不要只替换 test_lvgl，也不要先在旧升级器上使用增量包。

以后正常 `make` 自动生成：

- `images/UN260_UPDATE.upk`：完整包，可用于修复或基线不匹配的板子。
- `images/UN260_UPDATE_DELTA.upk`：文件级增量包。
- `images/UN260_UPDATE_BASE.upk`：默认固定基线，只在不存在时创建，**不是每次 make 的上一版**。首次与完整包相同，所以首次增量通常是零变化包。
- `images/UN260_RELEASE.json`：目标版本完整文件哈希/大小/权限、基线 ID、变化和删除清单。

新版本支持 U 盘 `update/UN260_UPDATE_DELTA.upk` 原名；两种包同时存在时优先完整包。实际使用时只放需要安装的一个包，不要把 BASE 放入 update。增量包校验板上实际文件，不只相信版本号；基线不匹配应使用完整包。已经达到增量目标状态时，验证目标后直接报告无需替换。

同一固定基线用于“基线→目标版本”的升级。板子已经装过另一个中间版本，不保证仍匹配该基线，此时使用完整包，或明确指定该中间发布包作为基线：

```sh
UN260_UPDATE_BASELINE=/absolute/path/to/released-full.upk make
```

不要删除/自动覆盖基线来追逐开发中间版本；对外发布后应归档完整包及清单。旧的裸 test_lvgl 升级路径仍保留，但不适合本轮应用/库接口一起变化的升级。

## 阶段一：统一资源预算

- 新 `aic_ui/image_memory.c` 管理 decoded image、DMA snapshot、GE scale、decoder temporary 四类 DMA 申请。正在构建但尚未加入缓存的资源也占预算，失败路径释放申请。
- 当前总预算 12 MiB；MPP 池为 16 MiB，留下 4 MiB 未分配余量。解码临时申请计入 bitstream 和 1 MiB 保守 scratch 预留。SDK 内部全部实际分配、framebuffer 及其他模块并非都被精确计量，不能将这个预算宣称为物理内存绝对保证。
- CPU 快照及紧凑行缓冲独立限制为 4 MiB，不与 DMA 剩余混为一谈。reserved heap 的备用分配也保守计入同一 DMA 总预算。
- 内存压力优先回收缩放衍生缓存、无引用快照、未被 pin 的解码图片。引用中的快照与正在绘制的图片不回收。GE 缩放回收仅允许已验证的 NORMAL 同步模式，不启用 CMDQ。
- 页面预热在剩余管理额度不足 2 MiB 时暂停。保留当前图片缓存 8 MiB 和快照缓存 8 MiB 各自上限，总量仍受共同预算约束。
- 开启现有 PERF 时，启动日志增加 `IMG_MEM` 各类别/current/peak/denied 统计；正常关闭 PERF 时不新增周期性内存日志。

预算是安全起点，需要板端连续滑动与切页验证后判断是否影响缓存命中和 FPS，不能承诺性能一定提升。

## 阶段二：失败兜底与可见对象重试

- 通用 `lv_draw_img` 失败时绘制原生浅灰底板/简洁图标，不依赖外部文件和解码内存，不显示 No data 文案。不会拿上一次不同故障的配图冒充当前故障。
- 普通图片缓存仍复用有效内容；失败不缓存成有效图片。故障文本、错误码和按钮与配图独立，原生故障弹窗底板保留。
- `lv_img` 通过可选通用观察接口通知应用恢复服务；最多跟踪 64 个失败对象，固定内存，无每次重绘动态创建队列。
- 失败对象在 1.5 秒、再 3 秒、再 6 秒后最多安排 3 次局部重试；每个 100ms tick 最多安排一个对象。不是阻塞等待，不全屏刷新。
- 删除事件立即解除所有权，隐藏或更换图片来源会清理对应任务。3 次仍失败的被跟踪对象进入兜底显示，不因连续重绘反复进行图片 I/O；重新显示页面/改变来源可重新尝试。队列容量不足时仍有原生兜底，但不保证每个对象都有定时重试名额。
- 正常图片、没有恢复任务时，观察接口直接返回，不扫描队列、不计算路径哈希。定时器无任务时暂停。
- 首次文件头失败也保留有效占位几何，避免 0×0 不可见对象和后续取模除零；恢复时重新读取头信息。
- 离屏捕获期间发生图片失败，会拒绝保存该不完整快照，保留 live-object 路径。

此机制不修复损坏文件或硬件故障，只提供安全降级及有限恢复；也不保证 LVGL 以外所有自绘资源都有相同重试行为。

## 阶段三：完整包提速

- 保留 SHA256+权限未变化跳过逻辑。
- `un260_unpack` 在私有 stage 内单遍 gzip/ustar 读取、路径检查、类型检查和解压；支持 regular/directory，拒绝 symlink/hardlink/device/PAX/GNU 扩展/重复文件/越界路径，限制条目及展开体积，检查 tar checksum 和 gzip CRC。使用 openat+O_NOFOLLOW+O_EXCL，不能覆盖 stage 外文件。
- 缺少新版 helper 时保留旧安全验证路径，用于首次完整包兼容部署。新 builder 使用 ustar 格式。
- 已校验 payload 的 SHA 不在安装计划中重复读取计算。备份 SHA 与计划中的原文件 SHA 比对，仍保留备份读取校验和写入后 SHA 校验。
- 零变化计划不创建事务、不做备份和替换。
- 同一目标百分比的 320ms 动画不再被 100ms 状态轮询反复重启。
- 安装阶段按变化文件字节数加权；单个大文件复制/同步期间仍可能停留在一个数值，不伪造匀速增长。日志增加阶段耗时、变化字节数和当前安装路径。
- 未删除 sync，未关闭空间预算、原子替换、旧 inode 保护、备份或恢复日志。

## 阶段四：安全文件级增量

- 主机 Python 工具从两份校验通过的完整包产生增量，包含新增/修改文件和明确删除清单；不做二进制差分。
- baseline/target 表包含 hash、mode、size、path，并与包元信息中的摘要绑定。所有外部依赖在板上核对，差异时拒绝，避免混装应用/库/资源。
- 没有出现在增量包中的文件不自动删除。退休资源只有显式 delete 才删除，沿用备份、old inode、事务日志及回滚；禁止删除核心程序、库、升级器和启动脚本。
- 保存原来的路径白名单、禁止符号链接及空间预检。文件摘要提供完整性检查，不是发布者签名；本轮未新增签名密钥体系。
- 增量包减少未变化文件的解包和处理，不改变“变化的大程序仍需整文件写入”的事实，也不能消除新旧程序共存所需根分区空间。

## 板端逐项验收

1. 首次仅用完整包，重启后查启动背景、Main、Currency、Menu、故障弹窗是否正常；查启动标记 `build=RESILIENCE_R1`。
2. 正常关闭 debug 测滑动、点击、切页，确认无明显 FPS 回退；再可选开启 PERF 记录 IMG_MEM，反复切页与开关弹窗至少 50 次，检查 current 占用是否趋于稳定。
3. 缺图/内存压力注入仅在可恢复测试板、已留样资源上进行，不能在客户机器随意删图片。检查配图异常不影响故障文字与退出、重试期间切页不崩溃。
4. 对比相同 U 盘、板子和同类型变化的升级总耗时，读取 U 盘 ui_update.log 中 UPGRADE_TIME、UNPACK_OK、Install plan。首次安装新升级器本身不能代表后续单遍解包速度。
5. 分别测试后续完整包和正确基线增量；再测试同包重复、错误基线拒绝。真实拔盘/断电测试需在可重新烧录的测试板上单独进行，未通过前不声明量产断电验证完成。
