# UN260 R8：统一升级与应用分区

2026-10-05：现场只交付同一份 `images/UN260_UPDATE.upk`。未扩容、已经扩容、工厂预置、前次失败和重复安装均使用此包；操作人员不选择内部应用包、迁移包或 delta。

## 使用

1. 停止点钞并确认所需记录已保存；保存原 U 盘日志及全部 `UN260_*BACKUP*`、`UN260_STORAGE_DIAGNOSTIC_*` 目录。
2. 将当前完整包放到 U 盘根目录 `update/UN260_UPDATE.upk`，在应用的升级入口确认升级。
3. 若提示需要继续重启，保持同一 U 盘和包，重启后等待迁移及应用安装。这一步表示接续已准备好，不是最终成功。
4. 已扩容设备由当前升级器直接安装完整应用，不重复初始化分区。旧升级器首次安装新机制可能仍需一次同盘接续。
5. 以最终 `result=success`、目标版本、应用卷和实际主界面共同确认完成；再核对原记录/设置及拔盘启动。

相同包仍可由用户再次确认安装。重复包指纹不替代对实际文件、权限和卷的校验；已全部匹配时不重复复制或格式化。

## 支持范围与数据

适用于本项目可运行升级器的 D211/D213 UN260 配置：mtd10=64 MiB `ubiroot`，mtd11=38 MiB `ubisystem`，2 KiB 页和 128 KiB 擦除块，根为 `ubi0:rootfs`。不改变物理分区表。目标运行布局为根启动器加 `ubi*:un260_app` 挂载到 `/mnt/un260-app`；库和资源仍归根分区。

V3 迁移在确认旧 mtd11 未被挂载、未被其他 UBI 使用后，保存原分区完整字节、原应用和布局证据，以本次源 SHA-256 和 UUID 绑定备份。持久写回、直接回读和源稳定检查通过后才初始化。不同旧内容不再仅因与单台样本指纹不同而失败。备份不是“旧分区为空”的声明，应独立保存。

业务数据由 `/etc/ui_state` 整树持有，包括冠字号/点钞历史、账本、工作区、工作模式、待机照片以及语言、密码、触摸、显示、截图和录屏等配置。升级不覆盖或清理此目录，也不覆盖触摸校准。应用维护的 `usr/local/share/lvgl_data` 静态资源按同一完整包收敛；用户导入照片位于受保护的数据目录。

当前 R8 应用在启动升级和重启前将当前记录提交到点钞历史，并等待历史、账本、工作区及待机保存完成。等待超过 30 秒会停止本次准备并允许重试；准备阶段可取消，已接受的保存任务继续执行。原主板清当前计数与重启流程保持，活动 RAM session 不会在重启后继续。旧应用首次接收新包时还未拥有这些新检查，因此升级前人工确认记录已保存仍是必要步骤。

统一的是包内应用、依赖、静态资源、升级组件和应用卷布局。UPK 不重刷引导、内核或整套基础 rootfs，也不能运行在没有可用升级执行入口的设备上。缺盘、只读/坏盘、设备读取或写回错误、容量不足、不匹配的硬件/挂载仍须停止并保留证据，不以成功状态掩盖这些故障。

## 恢复

- 旧三行 V1、五行 V2 日志保持恢复兼容。V3 五行日志绑定本次策略、源摘要、阶段、原应用摘要和 UUID；任何可能再次初始化的接续必须核验原备份。
- 文件替换和资源删除归同一持久事务；中断先恢复或回滚，不删除 pending、active 或事务来绕过检查。
- 开机自动接续只接受已安装请求绑定的同一包。在可用主界面明确安装新包才可更新请求；旧未完成状态仍须先安全恢复。
- 迁移未开始且旧应用可运行，或已激活卷稳定且没有待恢复事务时，失败可返回已验证的现有应用供重试。失败结果保持失败，不发布完成标记。
- 已激活卷损坏、归属冲突或未知挂载不自动格式化。旧 R7 启动器若根本不能返回应用，也不能由它拒绝执行的新包自行修复，需对应维修入口。

## 构建与核验

```sh
make test-lvgl-rebuild
UN260_UPDATE_VERSION=1.0.0-r8-unified-20261005 make
```

完整 make 生成匹配的工厂 IMG、内部完整应用和唯一当前对外统一包；核对嵌套摘要、策略能力、目标字节/权限、IMG 的 root/app 及版本。`un260_internal/` 全部是构建中间文件，不要求现场切换。固定 R7 归档不覆盖、不冒充当前 R8。

主机回归覆盖正常、拒绝、备份/写回失败、阶段中断、回滚、旧状态兼容、已扩容更新、资源收敛和重复包。交叉编译和目录模拟不替代真实 NAND 掉电、无盘启动、显示/触摸和本地数据保留的实机验收。
