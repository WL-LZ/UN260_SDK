# UN260：首次扩容与日常直接升级

2026-09-29 更正：已扩容/工厂预置应用卷的设备，日常升级恢复为当场安装完整程序。R7 把两阶段统一迁移包作为所有设备的默认升级包，导致每次都先装接续组件、重启后再装应用；这是发布包选择的问题，不是已扩容机器的必要限制。

目标是两条入口、同一套最终存储布局，而不是要求每台机器先烧 IMG 再升级 UPK。

## 设备处理矩阵

| 设备情况 | 正确入口 | 是否再装扩容包 |
| --- | --- | --- |
| 全新、与当前硬件配置匹配的空白核心板 | 本次工厂 IMG，一次完整烧录 | 不需要；首次开机无 U 盘也应进入主程序 |
| 有旧程序、UPK 升级入口正常、分区布局及旧内容在审核范围内 | 首次迁移专用 `UN260_FIRST_MIGRATION.upk`，复制改名为 USB `update/UN260_UPDATE.upk`，保持同盘重启接续 | 不需要人工切包；内部完成迁移及应用安装 |
| 已升级 R6 或以后版本、应用卷正常 | 日常 `images/UN260_UPDATE.upk` | 当场安装完整应用；完成后重启仅启动新程序 |
| 已烧新工厂 IMG，以后更新功能 | 日常 `images/UN260_UPDATE.upk` | 当场升级；不再进入重启接续升级页 |
| 烧的是旧 IMG | 不能据此认定已经预置新布局 | 新板应直接使用新工厂 IMG；已有数据按旧板 UPK 路径 |
| 停在此前 R4/R5 的已知故障 | 先确认没有运行中的升级，保留备份并按维修流程安装当前接续组件，再同盘重启 | 不清 pending/active/事务，不盲目重刷 |
| 没有可用系统/升级入口，或内核、引导损坏 | 工厂/维修烧录或专门恢复 | UPK 不负责修复引导；既有数据先评估备份 |
| 不同 NAND 几何、不同核心板/屏幕配置、未知分区内容 | 停止并审核硬件、镜像与数据 | 不强制迁移，不用当前 IMG 碰运气 |

“同型号”不等于每台 NAND 内容都相同。当前自动迁移仍只允许审核过的精确数据指纹；不同批次遇到不匹配，需要先检查样本备份，不能直接放开擦除。现有成功 R6 设备无需为容量问题马上重刷 R7；先在备用新板和旧板样本上验收本次版本。

## 支持范围和数据边界

- 当前构建面向项目 D211/D213 配置，128 MiB SPI NAND、2 KiB 页、128 KiB 擦除块；mtd10 根分区 64 MiB、mtd11 应用分区 38 MiB。DDR、显示、触摸及外设必须与现有板级配置匹配。
- 不改变物理分区表，不吞并 kernel/recovery，也不提供尚未实现运行时支持的 4 KiB/256 KiB NAND 变体。
- 工厂 IMG 覆写系统及应用分区；把已有设备当新板烧会丢失记录/设置，应视为有授权的重置。校准、设备身份等其他分区也不能仅凭 IMG 扩展名假设保留，须按烧录器选项核对。
- UPK 只更新允许的应用、库、资源和必要系统组件。业务记录、用户配置不作为清理目标；迁移初始化 mtd11 前必须有校验通过的持久备份。
- 应用运行于 `/mnt/un260-app/test_lvgl`；根路径保留启动器。库、图片和业务记录仍在根分区。两处空闲不能相加当成任何文件都能使用的一个池。
- 已实测 R6 样本为根可用 19572 KiB、应用卷可用 26820 KiB；这不是每块新板的保证值。保留升级临时副本和安全余量，增加字体/语言/动画仍需控制各自分区体积。

## 按设备状态选择发布入口

- 工厂人员拿 `factory/*.img`；一次完整烧录后移除烧录介质，正常启动，不再做 USB 扩容。
- 已扩容/新工厂 IMG 设备拿默认 `images/UN260_UPDATE.upk`，放到 USB `update/UN260_UPDATE.upk`。点击升级后直接校验、备份、替换和核对完整程序；成功后 Reboot 启动新版本，不应再次进行维护安装。当前已扩容设备的旧升级器也支持这一格式，无需先安装新升级器再多重启一轮。
- 只有尚未迁移的受支持旧设备才使用 `images/un260_internal/UN260_FIRST_MIGRATION.upk`，复制改名到同一 USB 路径。此包首次成功只是接续准备完成，保持同盘重启后完成首次扩容和应用安装。已开始但未完成的迁移先按原恢复流程处理，不删除标记、不换普通包跳过。
- 最终成功并进入主程序后，正常关机取盘，或通过已有安全卸载流程取盘，再处理下一台。无需回电脑换成第二/第三个包。
- `images/un260_internal/` 保存应用构建副本、首次迁移专用包、bootstrap、delta 和固定增量基线。只在明确首次迁移的场景分发 `UN260_FIRST_MIGRATION.upk`；其他中间文件不用于现场选择。包校验提供完整性，不提供发布者签名认证。
- `images/UN260_STORAGE_EXPANSION_R7_20260929.upk` 为人工固定归档的 R7 扩容迁移包，含当时应用；普通 make 不覆盖。只有作为旧机迁移备用时才复制并改名为 U 盘 `update/UN260_UPDATE.upk`，不要把它误认为最新版。删除整个输出目录会连此归档删除，应保留独立交付备份。

## 失败与中断

| 情况 | 程序处理 / 现场动作 |
| --- | --- |
| U 盘坏簇链、只读、掉线或写回失败 | 停止，不宣布最终成功。保留 RAM 日志和已有备份；换盘前备份并排查，不强制 remount rw |
| 重启时没插原盘/包不匹配 | 暂停等待同一包，不假装升级完成；恢复正确介质后再接续 |
| 写文件失败、安装中断 | 依持久事务恢复或回滚；保留锁、事务和备份，不手动删标记 |
| 扩容进行中断电 | 依迁移阶段恢复；涉及格式化阶段需原 USB 备份，不能拿其他包硬接续 |
| 已激活卷无法挂载、owner/启动器不匹配 | 停止应用启动并报告，不自动格式化，也不偷偷运行过期根程序 |
| 根/应用/USB 容量不足 | 各自预检拒绝；不靠降低安全余量或清记录“解决” |
| 不同旧分区内容/几何 | 停止并留证，不擦除未知数据；对批次另行审核 |

目录模拟和写回错误注入不等于真实 NAND/UBIFS 掉电验收；有恢复条件的测试板上才做受控断电，不在客户生产记录上试验。

## 构建与防止混包

```sh
make test-lvgl-rebuild
UN260_UPDATE_VERSION=1.0.0-fleet-20260929-r7 make
```

完整构建默认：

1. 不改普通 `output/.../target` 的应用 ELF；在独立 UBIFS fakeroot 副本中生成启动器与 active 标记。
2. 离线生成必需的 `un260_app_page_2k_block_128k.ubifs`，含匹配 ELF 和 owner。不使用开机格式化脚本。
3. 工厂 IMG 强制包含 rootfs、应用卷和正确卷名环境；拒绝把升级请求、事务或客户状态打入新机。
4. 默认对外 `images/UN260_UPDATE.upk` 必须是 `package_type=ui` 的完整包，安装清单直接包含应用，不含 unified-request 或迁移内包。首次迁移包单独保存在内部目录，固定 R7 扩容归档不覆盖。
5. 构建门禁分别核对日常直接包和首次迁移包；核对 IMG 组件 CRC、卷名、版本和 base ELF，全部通过后再原子发布日常包及摘要。发布时额外从实际 IMG 解读 UBIFS 并逐文件核对。

IMG 外层 SDK 版本字段仍为基础 `1.0.0`；实际应用版本在 `/etc/un260/package-version`。交付目录名及 SHA-256 标识具体批次，不通过重新命名旧文件冒充新固件。

## 首批板上验收（R7 仍待执行）

1. 备用新板一次烧本次 IMG，不插升级盘：确认主程序、触摸/显示/协议、版本和两个挂载；重复断电开机不出现升级等待。
2. 受支持的未迁移旧板使用首次迁移包完成扩容；重启后确认旧记录/设置/用户图片及新版本，再无盘启动。
3. 已完成 R6 的板用普通 UPK 更新：点击升级后应用已安装，Reboot 后直接进入新程序；应用卷不重建、数据不清除，不重新进入维护升级页、不再提示安装同一包。
4. 确认未来包仍走 UPK；抽查错误包/缺盘/只读盘停止路径。物理断电恢复另在可恢复样机上验证。

最终成功的只读检查：

```sh
cat /tmp/ui_update.status; cat /etc/un260/package-version; df -k / /mnt/un260-app
```

工厂新机没执行 USB 升级时 `/tmp/ui_update.status` 不存在是正常的；正常重启也会清空 `/tmp`。以版本、挂载和实际运行状态综合判断，不将历史 100% 或某一张画面当作唯一依据。
