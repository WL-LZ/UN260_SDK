# UN260 生产升级基座与现场升级

2026-10-09：生产机先统一烧录包含 `UN260_UPDATER_PLATFORM_V1` 的匹配工厂 IMG。此后日常软件更新使用正常 `make` 生成的同一个 `images/UN260_UPDATE.upk`，不需要先安装特殊桥接包。更早 IMG 和嵌套迁移包属于历史配置，不混作当前生产交付。

## 操作流程

1. 停止点钞，完成当前记录、账本、工作区及设置的保存。保留以前产生的备份和日志。
2. 把正式包放到 U 盘 `update/UN260_UPDATE.upk`，通过屏幕 UI 升级入口开始一次升级。
3. 安装成功后按提示正常重启。安装结束表示文件已核验并持久写回；启动确认发生在重启后。
4. 新程序实际显示第一帧并稳定运行后，系统确认本次更新，再释放配套旧文件。若新版不能正常显示，恢复完整旧配套或进入独立 U 盘维护界面。
5. 核对主界面、语言、原记录与设置，并验证拔盘启动。不要通过删除事务或归属标记强迫显示成功。

正在等待上次安装重启确认时，再次升级应提示先重启。插盘的正常启动不会自动安装新包；只有 UI 无法恢复时，独立维护流程接受正式包修复。

## 数据、兼容性与速度

硬件基座对应本项目 D211/D213、2 KiB NAND 页与 128 KiB 擦除块、既定物理分区。根为 `ubi0:rootfs`，出厂应用卷为 `un260_app`，挂载到 `/mnt/un260-app`。首次开机只检查归属并挂载已预置卷；普通 UPK 不初始化或格式化 NAND。

程序、库、启动运行时、静态资源、开机动画或 logo 资源，以及升级引擎和工具在同一包内绑定。固定 dispatcher、启动入口和出厂救援副本由 IMG 建立，普通 UPK 禁止覆盖。包内引擎负责后续更新的校验与恢复，避免仅更新磁盘脚本却继续运行旧 shell 逻辑。

完整包列出全部目标的 SHA-256、权限和长度，逐文件比对后只替换变化内容；已匹配文件跳过。完整包仍需读取、解压和核验，因此实际耗时还取决于包大小、U 盘与 NAND。不能仅凭修改行数承诺固定秒数。

`/etc/ui_state` 整树及触摸校准保持客户所有，包括历史、冠字号、账本、工作区、语言、密码、照片和其他配置。完整包仅收敛程序拥有的静态资源，不清理客户导入数据。时间设置不作为启动确认或恢复等待的依据。

当前 UI 的升级准备和重启仍需等待业务持久化完成，保留协议确认、清计数及正常重启流程；准备阶段可以取消，已进入文件安装的事务必须完成或恢复。

普通软件、升级器与显示资源可以沿该基座更新。BootROM、物理 NAND 几何、内核与驱动 ABI 或容量超出基座的改动不属于普通应用 UPK，需在开发阶段另行评估；损坏、只读、拔盘和写回失败不能被掩盖成成功。

## 恢复机制

- 文件事务保留原 inode，未提交中断优先回滚；提交后的候选程序保留整套旧配套，直到真实显示且存活确认。
- 升级包内引擎、存储屏障、解包、挂载和维护工具先复制到受限 RAM 私有目录，保持同一个进程与升级锁，避免替换自身时混用版本。
- 回滚先持久保存决策，然后幂等恢复旧启动描述符和完成记录，再恢复文件；确认或回滚的清理过程可中断续做。
- 正常启动运行时损坏时，固定入口选择出厂副本；独立看护发现 UI 不存活时进入维护路径。维护显示和修复入口不依赖新 UI 的库。
- 已激活卷损坏、归属冲突和未知挂载保持诊断，禁止自动格式化。恢复日志和备份均不能擅自删除。

## 构建与验收

正常完整 `make` 输出匹配 IMG、唯一正式 UPK、摘要和深度核验记录。构建检查目标代码、完整资源、运行时描述符、固定救援层、内核启动能力，以及 IMG 内真实 root/app 内容；内容版本区分同名 dirty 源码构建。

验证必须分别记录主机/BusyBox 故障注入、交叉构建、包和 IMG 内容核对、板上屏幕升级、新旧程序启动、无盘启动和客户数据保留。主机模拟不代表真实 NAND 掉电验证，完整编译也不代表显示、触摸或升级耗时已经实测。
