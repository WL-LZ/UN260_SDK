# UN260 R8 历史嵌套迁移流程

本文件记录旧 IMG 的 R8 桥接与迁移机制，默认生产构建已停止发布此嵌套包。当前生产基座与直接完整 UPK 交付规则见 [FACTORY_FLEET.md](FACTORY_FLEET.md)。所有支持的在用设备使用同一 `update/UN260_UPDATE.upk`；默认完整 make 发布统一包，不再要求现场区分首次迁移与日常完整应用包。

外包沿用旧升级器支持的 schema 1 和小型接续清单。内含同一版本的迁移、完整应用及摘要请求，内包保留在 U 盘。未扩容机器先安装接续组件，同盘重启后验证完整应用、持久备份原分区和应用、迁移、安装及最终核验。当前升级器在已有健康应用卷时直接完成应用更新；不重复初始化卷。

准备接续写 `stage=restart` 和 `result=pending`，仅最终卷/应用/库/资源/组件及写回核验成功后写 `result=success` 和完成标记。旧升级器首次处理新外包仍可能显示其原有成功提示；当时只是小型接续阶段完成，必须等待重启接续后的最终结果。

V3 `un260-backed-up-legacy-v3` 允许受支持且未使用的历史分区内容不同，前提是原字节、应用和布局已经校验备份，源摘要再次稳定，备份以独立 UUID 绑定。V1/V2 日志恢复保留；旧策略不能解释或接续 V3 日志。未知挂载、布局错误、读取/备份/写回错误不初始化。

程序文件和静态资源的新增、替换与删除使用同一持久事务，失败先恢复。重复包仍检查实际内容；版本文字或 FNV 指纹不代表安装目标正确。最终完成须有健康应用卷、目标哈希/模式、无未恢复事务，以及与当前请求匹配的 `unified.completed`。

`/etc/ui_state` 整树、触摸校准和其他不在安装清单中的本地业务数据受保护。不同设备保存的记录、照片、用户开关和设置可以不同；升级软件和静态资源目标相同。

历史 R4/R5/R6/R7 故障证据及归档保留在对应交付目录，不能把旧包改名当成本次 R8。所有支持状态和真实硬件限制见当前交付规则；无可用系统/升级入口时仍需维修入口。
