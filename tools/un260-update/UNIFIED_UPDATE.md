# UN260 首次迁移统一包：一次拷贝，同盘接续

**2026-09-29 日常发布规则已更正：默认 `images/UN260_UPDATE.upk` 是直接安装的普通完整包。本文的两阶段流程仅适用于 `images/un260_internal/UN260_FIRST_MIGRATION.upk`（首次扩容专用），以及已开始迁移的故障恢复。已扩容设备不再使用此包做日常更新。**

## R7：工厂 IMG 与现场 UPK 统一布局

当前交付规则及新板/旧板/故障板的适用边界见 [FACTORY_FLEET.md](FACTORY_FLEET.md)。本次更正后的完整 `make` 默认生成已预置应用分区的工厂 IMG，以及日常直接更新的 `UN260_UPDATE.upk`。新板烧录此 IMG 后不需要再执行扩容包；只有未迁移的支持设备走首次迁移专用 UPK。以下 R4/R5/R6 是历史故障记录，不是要求现场依次安装的版本链。

R7 将手动升级和重启接续的原始外包指纹也写入 UI 共用的 `installed.fnv64`，修复最终成功后重新进入主页面还提示安装同一包的问题。内部包不会覆盖外包身份，USB 写回失败不发布新的成功标记。该 FNV 仅用于重复包识别，不代替 SHA-256 校验或发布者签名。

## R6：修复 R5 资源清理路径循环

2026-09-29 板上确认：`busybox dirname //usr` 与 `busybox dirname //` 均输出 `//`。资源清理器的 `ROOT=/` 和 `/relative` 拼接产生 `//usr/...`，旧 `safe_path` 只在 `/` 或 `.` 停止，因而在第一项资源检查前循环。此时迁移日志已显示 committed，但应用安装尚未开始；34% 不是升级完成，也不是继续格式化的理由。

R6 在 Linux 路径检查中归一化重复前导斜杠，并要求父路径遍历每步成功且前进。所有路径组件的符号链接检查、固定哈希清单、完整备份和写回校验保留。清理名单没有扩大，业务应用、库、图片、协议和迁移流程不变。实际生成的脚本及真实清理器参与的统一升级流程已补充 BusyBox 回归；临时目录测试需保留 `//` 路径形态，不能只换 BusyBox shell 而漏掉真实根路径。

已卡住的 R5 设备：先确认进程身份和停止位置，再正常终止循环子进程，让父升级器报告失败并释放锁。不要 killall、强杀主升级器或删除 pending/active/锁/事务。确认升级与清理进程均已退出后，卸载 U 盘或正常关机取盘；保留全部备份，只替换为 R6 的 `update/UN260_UPDATE.upk`。插回后先手动运行 `sh /usr/bin/ui_update.sh` 安装新接续组件；第一轮成功后才保持同盘重启。不能只换包重启，旧请求仍会拒绝不匹配的包。

已经 committed 的应用分区会按 active 状态复用，不要求重新初始化。当前机器仍需实机确认最终进入应用、版本为 R6、原数据完整及无盘启动，再推广其他同布局和审核指纹的机器。终端若将多行粘贴合并，使用单条命令或明确的英文分号。

## R5：R4 暂停设备的一次性恢复

2026-09-29 板上确认 R4 调用了目标系统没有的 `cmp`，将命令缺失误报为升级包变化。R5 用现有 SHA-256 进行失败即停止的一致性检查，并分别报告读取失败和内容不匹配；没有取消请求或接续组件的校验。

同次排查还发现 U 盘 FAT 无效簇链、被内核置为只读。R5 不修复或格式化 U 盘、不强制重新挂载为可写：暂存清理失败立即停止，创建目录的底层错误进入 RAM 升级日志，失败画面不再让所有故障盲目重启，也不保证错误日志已写入坏盘。

已暂停在 R4 的设备：保留原盘和 NAND 备份，使用正常文件系统的 U 盘放入 R5 的同一个 `update/UN260_UPDATE.upk`。确认无升级进程后正常关机换盘，开机暂停后，在串口执行 `sh /usr/bin/ui_update.sh`；仅在 `/tmp/ui_update.status` 显示 `stage=success`、`success=1` 时，保持该 U 盘重启，让 R5 自动接续。不能直接换成新包就依赖旧 R4 的有缺陷接续代码。不要删除请求、迁移 pending 或跳过校验。

此路径已用冻结的交付 R4 脚本和缺少 cmp/stat/tail 的命令故障注入验证；仍需板上验收。未安装 R4 的设备继续走原升级入口，不需这次串口修复。

## 操作方式

1. 此流程仅用于首次扩容：将首次迁移专用包复制并改名到 U 盘 `update/UN260_UPDATE.upk`。盘上有效包为 `update/UN260_UPDATE.upk`，不要混用此前 01/02/03 分包。保留已有 NAND、应用和资源备份。
2. 插入机器，在原有升级入口执行一次升级。
3. 首次显示成功/建议重启时，**U 盘不拔、不换包**，按正常方式重启机器。旧升级器这一步的“成功”只代表接续组件已装好。
4. 重启后自动显示维护升级画面，依次核验完整程序包、备份并校验旧内容、准备应用分区、安装程序和检查写入。不要断电、拔盘或启动点钞。
5. 最终完成后自动进入应用。先在首台确认版本、页面和原有记录，再关机取盘，用同一盘处理下一台。不需要返回电脑切换包，不需要刷 IMG。

首次包适用于已审核的同布局/同旧分区内容机器。其他机器不因型号相同就被允许清空：几何、挂载或指纹不匹配会暂停。首台实机验收之前，不建议直接推广到整批。

若显示 `UPDATE PAUSED`，保留盘内备份和 `ui_update.log`。U 盘未连接等可恢复问题，排除原因后保留同一包重新启动；分区不匹配不要反复尝试格式化。已安装请求但尚未完成时，启动不会进入点钞程序，以免把半完成的升级当成可用状态。

## 实现与边界

- 外包是旧升级器支持的 schema 1。`install.tsv` 只安装 7 个小组件/请求文件，不包含大应用，也不把内包写入根分区。
- 两个内部包随外包一起保留在 U 盘：受指纹约束的迁移包和匹配的完整程序包；用户不操作它们。
- 重启接续入口在应用进程启动前执行；必须有本机安装的请求，且与当前 U 盘包逐字节匹配。普通开机、普通完整包、IMG 本身不会触发初始化。
- 先验证完整应用包和安装目标，再执行独立的分区迁移，再执行文件替换事务。内阶段不会发布整个升级成功。写回检查、USB 结果落盘和本机完成记录均成功后，才发布最终成功。
- 迁移仍只操作 `mtd11=ubisystem` 的 38 MiB，要求 `mtd10=ubiroot` 64 MiB 和指定根挂载。数据指纹固定为 `e19b211e20f31ce8d82c1e40b6fe3feca04e758f887c17beb976e444ab964b17`。未知内容不擦除。
- NAND 校验改为本地工具限长 `read()` 后交给 SHA-256 的标准输入，避免设备上 `sha256sum /dev/mtd11` 的 mmap 失败；读取失败与指纹不匹配分别报告。
- 原 NAND 备份以分区内容指纹保存；不同旧应用以自身 SHA-256 命名保存。可继续使用此前同内容的 `test_lvgl.before`，不会覆盖另一台不同版本的备份。
- 应用迁入 `/mnt/un260-app`；根分区大小没有增加，旧大应用占用被释放。新分区仍有有限容量，不承诺无限扩展。已有资源和业务记录不迁入此卷。
- R7 曾对已迁移设备也默认分发两阶段迁移包，现已撤回这一发布策略。日常对外 `UN260_UPDATE.upk` 与完整应用包字节相同，直接安装。两阶段包使用内部明确名称 `UN260_FIRST_MIGRATION.upk`，仅供首次迁移。
- 维护提示复用既有原生显示租约和 framebuffer FD 交接，不初始化业务协议/电机。未完成或失败时保留提示；成功后把显示权交给 LVGL。
- 极早期存储恢复失败、无法取得显示设备等仍需查看启动日志；不能用自动接续掩盖底层故障。

## 构建

完整 `make` 默认同时生成工厂镜像、日常直接升级包和独立的首次迁移包。迁移包只接受既定的审核指纹；几何或内容不匹配的旧设备不会自动初始化：

```sh
make test-lvgl-rebuild
UN260_UPDATE_VERSION=1.0.0-fleet-20260929-r7 make
```

日常对外输出 `images/UN260_UPDATE.upk`；首次迁移使用 `images/un260_internal/UN260_FIRST_MIGRATION.upk`，复制并改名为 U 盘 `update/UN260_UPDATE.upk`。不再生成重复的 `UN260_UNIFIED_UPDATE.upk` 别名；`UN260_APPLICATION.upk`、bootstrap、delta 和固定增量基线均放在 `images/un260_internal/`，不与现场交付混在一起。旧目录中已有的固定增量基线会被保留采用，不能重置成当前版本。`UN260_MIGRATION_APPROVED` 若设置也只能是精确审核指纹，不能传入通配规则。

另行归档的 `images/UN260_STORAGE_EXPANSION_R7_20260929.upk` 是固定 R7 旧机扩容基线（含 R7 程序），不是每次 make 生成的文件。正常 make 不覆盖它；使用时复制并改名为 U 盘的 `update/UN260_UPDATE.upk`。删除整个 output/images 或执行会清除此目录的 clean 会丢失归档，仍应保留工作站的交付副本。

本机请求 `/etc/un260/unified-request`；最终完成记录 `/var/lib/un260-updater/unified.completed`。迁移的 `pending/active` 和应用替换事务仍各归原有模块所有，完成请求不能替代这些实际检查。

## 验证范围

主机用例覆盖旧升级器接收、同包接续、错误 U 盘/请求、缺失组件、非法完整包提前拒绝、迁移失败、复制失败后回滚与重试、写回失败不发布成功、无请求普通启动、跨机器备份不覆盖。另有 NAND 限长读、迁移中断、事务回滚和显示 FD 交接测试。

主机目录/假 framebuffer 测试不等于实际 NAND 掉电、触摸或实机启动验收。交叉编译和完整 make 通过后，仍需首台实测：首次升级与重启接续、进入新应用、拔盘后启动、旧记录保留，以及合适条件下的受控失败恢复。
